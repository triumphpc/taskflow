## ADDED Requirements

### Requirement: Отдельный чекбокс делегирования в строке задачи

Строка задачи SHALL содержать отдельный чекбокс «Делегировать агенту», не совпадающий с галкой
выполнения. Чекбокс SHALL быть доступен только для не закрытых задач со сроком «сегодня» или
раньше (просроченные включены). Для задач на будущую дату, без срока и для входящих чекбокса
быть MUST NOT.

Нажатие на чекбокс MUST NOT открывать карточку задачи и MUST NOT начинать жест перетаскивания
строки. Если у задачи уже стоит статус агента (например, после повтора серии), чекбокс SHALL
оставаться доступным и снимать делегирование.

#### Scenario: Чекбокс отличен от галки выполнения

- **WHEN** пользователь открывает «Сегодня»
- **THEN** в строке задачи есть чекбокс делегирования, отдельный от галки выполнения
- **AND** нажатие на него не открывает карточку и не запускает перетаскивание

#### Scenario: Чекбокс доступен только для «Сегодня» и просроченных

- **WHEN** в списке есть задачи со сроком сегодня, просроченные, на будущую дату и без срока
- **THEN** чекбокс показан у задач со сроком сегодня и у просроченных
- **AND** у задач на будущую дату и без срока чекбокса нет

#### Scenario: Постановка делегирования

- **WHEN** пользователь отмечает чекбокс у не закрытой задачи на сегодня
- **THEN** задача получает статус агента `delegated`
- **AND** задача остаётся в списке

### Requirement: Статусы агента и допустимые переходы

У делегированной задачи SHALL быть ровно один из статусов агента: `delegated`, `in_progress`,
`review`, `needs_info`, `failed`; отсутствие статуса означает, что задача не делегирована.
Названия в интерфейсе: «Делегирована», «В работе у агента», «Выполнена агентом (на проверке)»,
«Нужно уточнение», «Агент не справился».

Допустимы только переходы `delegated → in_progress`, `in_progress → review | needs_info | failed`
и снятие делегирования из любого статуса. Повтор серии возвращает задачу в `delegated`. Прочие
переходы MUST быть отклонены: серверные операции возвращают отказ с причиной, клиентские
функции ничего не меняют.

Статус `review` MUST NOT менять признак `done`: задача остаётся открытой и в списке.

#### Scenario: Допустимые переходы

- **WHEN** сервер получает захват задачи в статусе `delegated`, затем завершение с результатом
- **THEN** статус последовательно становится `in_progress` и `review`
- **AND** `done` остаётся `false`

#### Scenario: Недопустимый переход отклонён

- **WHEN** запрошено завершение задачи, которая не находится в статусе `in_progress`
- **THEN** операция отклонена с причиной `not_in_progress`
- **AND** статус и заметки задачи не изменились

#### Scenario: Результат на проверке остаётся в списке

- **WHEN** агент перевёл задачу в `review`
- **THEN** задача остаётся в списке и закрывается обычной галкой выполнения

### Requirement: Подсветка строки тремя цветами и текстовый бейдж

Делегированная строка SHALL быть выделена одним из трёх цветов по группам статусов:
«делегирована / в работе» (`delegated`, `in_progress`), «выполнена агентом» (`review`),
«нужно уточнение / не справился» (`needs_info`, `failed`). Строка SHALL оставаться в списке,
пока задача не закрыта.

Строка SHALL показывать короткий текстовый бейдж статуса. Статус MUST быть доступен
вспомогательным технологиям текстом, а не только цветом. Превью результата в строке MUST NOT
показываться.

#### Scenario: Три цвета по группам статусов

- **WHEN** в списке лежат задачи в статусах `delegated`, `in_progress`, `review`, `needs_info`, `failed`
- **THEN** `delegated` и `in_progress` имеют один цвет, `review` другой, `needs_info` и `failed` третий
- **AND** все строки остаются в списке

#### Scenario: Статус читается текстом

- **WHEN** у строки есть статус агента
- **THEN** в ней виден текстовый бейдж статуса
- **AND** название статуса доступно как текст для скринридера

### Requirement: Очередь делегированных задач

В очередь агента SHALL попадать не закрытая задача в статусе `delegated`, срок которой «сегодня
или раньше» по локальной дате Mac. Время суток в сроке MUST NOT учитываться. Задача, не взятая
в прежний день, SHALL оставаться в очереди и браться в следующий. Порядок: дата срока по
возрастанию (просроченные первыми), затем момент постановки делегирования, затем приоритет.

#### Scenario: Задача на сегодня берётся независимо от времени суток

- **WHEN** делегирована задача со сроком «сегодня 23:00», а прогон идёт утром
- **THEN** задача входит в очередь этого прогона

#### Scenario: Невзятая вчера задача берётся сегодня

- **WHEN** делегированная задача со вчерашним сроком не была взята вчера
- **THEN** она входит в очередь сегодняшнего прогона

#### Scenario: Будущая дата и входящие не попадают в очередь

- **WHEN** у делегированной записи срок завтра или она является входящим
- **THEN** в очередь она не попадает

### Requirement: Результат агента — черновик, закрывает задачу только пользователь

Результат агента SHALL записываться в `agentNotes` готовым черновиком, поле `notes` MUST NOT
изменяться. Закрывает задачу только пользователь обычной галкой выполнения. В интерфейсе MUST
NOT быть цикла доработки результата агентом, отдельного фильтра «На проверке» и уведомления
о завершении.

#### Scenario: Закрытие после проверки

- **WHEN** задача в статусе `review`, а пользователь проверил текст и поставил галку выполнения
- **THEN** задача закрыта, как любая другая
- **AND** `agentNotes` с результатом остались

#### Scenario: Нет лишних механизмов

- **WHEN** агент перевёл задачу в `review`
- **THEN** в списке разделов нет фильтра «На проверке»
- **AND** пользователю не отправляется уведомление
- **AND** в карточке нет кнопки доработки результата агентом

### Requirement: Закрытие и снятие делегирования прерывают агента

Пользователь SHALL мочь закрыть задачу или снять делегирование в любой момент, в том числе
пока задача в статусе `in_progress`. После этого статус агента SHALL быть очищен, ранее
записанные `agentNotes` MUST остаться, а агент на ближайшей проверке MUST прекратить работу
и ничего не записать в задачу. Если делегирование снято у задачи в `review`, результат
в `agentNotes` остаётся.

Возврат закрытой задачи в работу SHALL очищать статус агента: старое делегирование не
возвращается. Удаление задачи SHALL прерывать работу агента так же, как закрытие.

#### Scenario: Закрытие во время работы агента

- **WHEN** задача в статусе `in_progress`, а пользователь ставит галку выполнения
- **THEN** статус агента очищен
- **AND** агент на ближайшей проверке прекращает работу и ничего не записывает в задачу

#### Scenario: Снятие делегирования у задачи на проверке

- **WHEN** задача в статусе `review`, а пользователь снимает чекбокс делегирования
- **THEN** статус очищен
- **AND** результат агента в `agentNotes` остаётся

#### Scenario: Возврат закрытой задачи

- **WHEN** пользователь возвращает в работу закрытую задачу, у которой было делегирование
- **THEN** статус агента не восстанавливается

### Requirement: Повторяющаяся задача сохраняет делегирование

Закрытие делегированной повторяющейся задачи SHALL переносить срок на следующую дату серии,
оставлять делегирование и возвращать статус `delegated`. Метки захвата и завершения MUST быть
обнулены, результат прошлого повтора SHALL остаться в `agentNotes`. Правило срабатывает
независимо от того, на какую дату перенесён срок.

#### Scenario: Закрытие повторяющейся задачи

- **WHEN** пользователь закрывает делегированную задачу с повтором, у которой статус `review`
- **THEN** срок переносится на следующую дату серии
- **AND** статус становится `delegated`
- **AND** результат прошлого повтора остаётся в `agentNotes`

### Requirement: Сохранность данных при синхронизации

Слияние записей на сервере SHALL быть пофилдовым по блокам: пользовательские поля решает
большее `updatedAt`, блок `agent` — большая метка `agent.at`, `agentNotes` объединяются по паре
`(at, text)` и только пополняются. Запись, в которой нет ключей `agent` и `agentNotes`,
MUST NOT стирать их на сервере. Слияние MUST NOT удалять ни одну задачу: удаляет только
надгробие.

Входящий блок `agent` с недопустимым статусом или меткой из будущего (дальше суток) SHALL
отбрасываться целиком, серверный блок побеждает. Новые заметки агента длиннее предела
`NOTE_TEXT_MAX` или с меткой из будущего SHALL отбрасываться. Для задачи, уже известной
серверу, число заметок агента SHALL быть ограничено 200: сверх лимита новые не принимаются,
существующие не трогаются. Для задачи, которой на сервере ещё нет (восстановление или новое
устройство), лимит не применяется.

#### Scenario: Запись без блока агента не стирает его

- **WHEN** старый клиент синхронизирует правку заголовка записи без `agent` и `agentNotes`
- **THEN** на сервере сохраняются прежние `agent` и `agentNotes`
- **AND** заголовок обновляется по `updatedAt`

#### Scenario: Конкурентная правка человека и агента

- **WHEN** человек правит заголовок, а агент одновременно записывает результат
- **THEN** ни одна задача не удалена
- **AND** сохранены и правка человека, и результат агента

#### Scenario: Недопустимый входящий блок отброшен

- **WHEN** клиент присылает блок `agent` с неизвестным статусом или меткой из будущего дальше суток
- **THEN** блок отбрасывается, на сервере остаётся прежний блок

#### Scenario: Лимит заметок для известной задачи

- **WHEN** у задачи на сервере уже 200 заметок агента, а клиент присылает новые
- **THEN** новые заметки не принимаются
- **AND** существующие заметки не изменяются

#### Scenario: Восстановление без лимита

- **WHEN** задачи ещё нет на сервере, а клиент присылает её с заметками агента
- **THEN** заметки принимаются без ограничения по числу

### Requirement: Совместимость данных и клиентов

Существующий `data/taskflow.json` SHALL читаться без миграции, `SCHEMA` MUST остаться равным
`1`. Задача без блока `agent` SHALL вести себя как раньше, её JSON после нормализации MUST NOT
получать ключ `agent`. Нормализация в клиенте (`js/store.js`) и на сервере MCP (`mcp.mjs`)
MUST давать одинаковый результат на одних данных.

Старый закешированный клиент SHALL синхронизироваться с новым сервером без потери задач
и блока `agent`; новый клиент SHALL открывать и править задачи из старых данных без ошибок.
Корректность MUST NOT зависеть от обновления кэша клиента; версия кэша `sw.js` при этом
повышается, `js/agent.js` входит в оболочку.

#### Scenario: Снимок реальных данных читается без изменений

- **WHEN** снимок `data/taskflow.json` прогоняется через новую нормализацию
- **THEN** число и `id` задач не изменились
- **AND** у задач без `agent` ключа `agent` нет
- **AND** `SCHEMA` равен `1`

#### Scenario: Паритет нормализации

- **WHEN** одни и те же исторические формы записи проходят `normalizeTask` из `js/store.js` и из `mcp.mjs`
- **THEN** результат одинаков

#### Scenario: Старый клиент с новым сервером

- **WHEN** сервер держит задачу в статусе `review` с заметкой, а старый клиент без нового кода часами офлайн правит заголовок и синхронизируется
- **THEN** ни одна задача не потеряна
- **AND** блок `agent` и заметки на сервере сохранены

#### Scenario: Новый клиент со старыми данными

- **WHEN** новый клиент открывает данные, где нет поля `agent`
- **THEN** задачи открываются и правятся без ошибок
