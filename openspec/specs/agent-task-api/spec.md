## Requirements
### Requirement: Агент управляет задачами через набор инструментов

Сервер SHALL предоставлять девять инструментов, покрывающих то же, что умеет приложение:
`tasks_list`, `task_get`, `task_add`, `task_edit`, `task_snooze`, `task_done`,
`subtask_add`, `subtask_toggle`, `task_delete`.

`tasks_list` SHALL принимать раздел из набора `today`, `tomorrow`, `upcoming`, `someday`,
`all`, `done`, `overdue`.

#### Scenario: Чтение раздела

- **WHEN** агент вызывает `tasks_list` с разделом `today`
- **THEN** возвращаются задачи, попадающие в этот раздел по тем же правилам, что и в приложении

#### Scenario: Создание задачи со всеми полями

- **WHEN** агент вызывает `task_add` с названием, заметками, сроком, приоритетом и подзадачами
- **THEN** задача создаётся целиком за один вызов
- **AND** изменение уезжает на сервер синхронизации и доезжает до телефона

### Requirement: Задача адресуется куском id или названия

Инструменты, работающие с существующей задачей, SHALL принимать первым аргументом либо
начало идентификатора, либо фрагмент названия.

Если под фрагмент подходит ровно одна задача, инструмент SHALL выполнить действие.
Если подходит несколько — инструмент MUST вернуть список кандидатов и MUST NOT изменить
ни одну из них. Угадывать за пользователя запрещено.

Если не подходит ни одна — инструмент SHALL вернуть внятную ошибку, а не пустой успех.

#### Scenario: Однозначное совпадение

- **WHEN** агент вызывает `task_done` с фрагментом, под который подходит одна задача
- **THEN** задача отмечается выполненной

#### Scenario: Неоднозначное совпадение

- **WHEN** агент вызывает `task_edit` с фрагментом, под который подходят три задачи
- **THEN** возвращается список из трёх кандидатов с их id и названиями
- **AND** ни одна задача не изменена

#### Scenario: Совпадений нет

- **WHEN** агент вызывает `task_snooze` с фрагментом, которому ничего не соответствует
- **THEN** возвращается ошибка с указанием, что задача не найдена

### Requirement: Удаление требует явного подтверждения

`task_delete` без аргумента `confirm: true` MUST NOT удалять задачу. Вместо этого он
SHALL вернуть ошибку, содержащую название задачи, которую собирались удалить, чтобы
агент мог показать её пользователю и переспросить.

#### Scenario: Удаление без подтверждения

- **WHEN** агент вызывает `task_delete` без `confirm`
- **THEN** возвращается ошибка с названием найденной задачи
- **AND** задача остаётся на месте

#### Scenario: Удаление с подтверждением

- **WHEN** агент вызывает `task_delete` с `confirm: true`
- **THEN** задача удаляется с надгробием, как это делает приложение

### Requirement: Перенос срока сохраняет время суток

`task_snooze` SHALL менять дату, сохраняя время суток, если оно было задано.
Задача, назначенная на весь день, SHALL остаться задачей на весь день.

#### Scenario: Перенос задачи со временем

- **WHEN** задача назначена на сегодня 14:30 и агент переносит её на завтра
- **THEN** срок становится завтра 14:30

#### Scenario: Перенос задачи на весь день

- **WHEN** задача назначена на сегодня без времени и агент переносит её на понедельник
- **THEN** срок становится понедельником без времени

### Requirement: Правила дат едины для приложения и сервера

`mcp.mjs` SHALL импортировать функции дат и повторов из `js/core.js` — того же модуля, что использует
браузерное приложение. Сервер MUST NOT содержать собственной реализации разбора срока,
вычисления «ближайшего понедельника» или признака просроченности.

#### Scenario: Разбор срока совпадает с приложением

- **WHEN** агент задаёт срок текстом, который приложение понимает
- **THEN** сервер разбирает его в ту же дату, что и приложение

#### Scenario: Признак просроченности совпадает

- **WHEN** агент запрашивает раздел `overdue`
- **THEN** состав раздела совпадает с тем, что показывает приложение в тот же момент

### Requirement: Сервер не владеет файлом данных

`mcp.mjs` MUST NOT читать и записывать `data/taskflow.json` напрямую. Все чтения SHALL идти
через `GET /api/state`, все записи — через `POST /api/sync`; единственное исключение —
условные переходы статуса агента (`agent_claim`, `agent_finish`), которые SHALL идти через
`POST /api/agent/transition` того же `serve.mjs`.

Единственным владельцем файла остаётся `serve.mjs`, что исключает гонку на
read-modify-rename между двумя процессами. Условный переход SHALL выполняться в той же
очереди записи, что и синхронизация, и MUST NOT менять `updatedAt` задачи и её пользовательские поля.

#### Scenario: Запись идёт через API

- **WHEN** агент создаёт задачу
- **THEN** `mcp.mjs` отправляет дельту на `POST /api/sync`
- **AND** не открывает файл данных на запись

#### Scenario: Основной сервер недоступен

- **WHEN** `serve.mjs` не отвечает, а агент вызывает любой инструмент
- **THEN** возвращается понятная ошибка о недоступности сервера синхронизации
- **AND** не возвращается стектрейс

#### Scenario: Условный переход идёт через серверный маршрут

- **WHEN** демон вызывает `agent_claim`
- **THEN** `mcp.mjs` отправляет запрос на `POST /api/agent/transition`
- **AND** не открывает файл данных на запись

### Requirement: Агент кладёт и читает входящие

Сервер SHALL предоставлять три дополнительных инструмента: `inbox_add`
(`title`, `summary`, `source_kind`, `source_url`, `source_ref`), `inbox_list`
(что лежит неразобранным) и `task_comment` (`task`, `text` — дописать в `agentNotes`).

`task_comment` SHALL адресовать задачу теми же правилами, что и остальные инструменты:
одно совпадение — действуем, несколько — возвращаем кандидатов и ничего не меняем.

`tasks_list` MUST NOT принимать раздел `someday` — такого раздела больше нет; неразобранное
отдаёт `inbox_list`.

`task_add` без даты SHALL создавать входящее: правило «активная запись без даты — входящее»
одинаково для человека и для агента, обойти его через другой инструмент нельзя.

`inbox_add` MUST NOT принимать ни дату, ни приоритет: во «Входящие» кладётся сырьё, а
планирующие поля проставляет человек при разборе. Догадка агента о сроке («в письме
упомянуто 1 октября») SHALL попадать текстом в `agentNotes`, где видно, что это догадка.

#### Scenario: Агент кладёт письмо

- **WHEN** агент вызывает `inbox_add` с заголовком, выжимкой и ссылкой на письмо
- **THEN** во «Входящих» появляется запись с заполненным `source`
- **AND** выжимка попадает в `agentNotes`, а не в `notes`

#### Scenario: Агент смотрит, что не разобрано

- **WHEN** агент вызывает `inbox_list`
- **THEN** возвращаются только записи с `kind: 'inbox'`

#### Scenario: Агент добавляет задачу без дня

- **WHEN** агент вызывает `task_add` без даты
- **THEN** созданная запись получает `kind: 'inbox'`
- **AND** попадает во «Входящие», а не в список задач

#### Scenario: Раздела someday больше нет

- **WHEN** агент вызывает `tasks_list` с разделом `someday`
- **THEN** инструмент отвечает ошибкой о неизвестном разделе

#### Scenario: Агент знает срок из письма

- **WHEN** в письме назван срок, и агент кладёт входящее
- **THEN** срок попадает текстом в `agentNotes`
- **AND** поле `due` у записи остаётся пустым

### Requirement: Агент наполняет входящие только по просьбе

Агент SHALL класть во «Входящие» только то, о чём его попросили, либо по явно оговорённым
с пользователем правилам разбора. Агент MUST NOT проходить по почте и чатам по собственному
расписанию и наполнять раздел без запроса.

Правило существует, чтобы раздел не превратился во второй непрочитанный ящик — риск,
ради которого затея теряет смысл.

#### Scenario: Разбор по просьбе

- **WHEN** пользователь просит агента разобрать почту за сегодня
- **THEN** агент кладёт найденных кандидатов во «Входящие»

#### Scenario: Без просьбы ничего не происходит

- **WHEN** пользователь не обращался к агенту
- **THEN** во «Входящих» не появляется новых записей

### Requirement: Служебные инструменты демона делегирования

Сервер SHALL предоставлять три дополнительных инструмента для демона делегирования:
`agent_queue`, `agent_claim`, `agent_finish`. Они SHALL работать через `/mcp` с тем же
Bearer-токеном, что и остальные инструменты. Описание каждого SHALL сообщать, что это служебный
инструмент демона и из диалога его вызывать не нужно. Новые инструменты SHALL добавляться
в конец списка, порядок прежних не меняется. Этот change не добавляет инструментов: число
и имена инструментов остаются прежними, меняются только необязательные поля ниже.

`task_id` в них MUST быть полным идентификатором задачи, фрагменты MUST NOT угадываться.

`agent_queue` SHALL принимать необязательные `today` (`YYYY-MM-DD`, по умолчанию дата
сервера) и `task_id`; результат: очередь, зависшие `in_progress` и, при указанном `task_id`,
состояние задачи (`exists`, `done`, `status`, `claimToken`), для несуществующей задачи
`exists: false`.

`agent_claim` (`task_id`, `today`) SHALL переводить `delegated → in_progress` и возвращать
`claimToken`. Рядом с `task` (не внутри него) ответ SHALL содержать ключ `journals`: блоки
журналов прежних попыток этой задачи с тем же сроком, от старых к новым, не больше трёх;
пустой массив, если их нет. Состав `task` MUST NOT меняться.

`agent_finish` (`task_id`, `claim_token`, `status`, `text`) SHALL переводить `in_progress`
в `review`, `needs_info` или `failed` и дописывать заметку; с `by_ttl: true` он SHALL
переводить зависший `in_progress` в `failed` без токена, только по истечении TTL.
`agent_finish` SHALL принимать необязательный аргумент `journal` (журнал действий прогона),
в том числе вместе с `by_ttl: true`. Сервер SHALL записывать `journal` в `agentNotes` первым
блоком результата, до текста, и применять к нему те же правила нормализации и слияния, что
к прочему тексту `agentNotes`. Если сервер принял непустой журнал, ответ SHALL содержать
`journalStored: true`; ответ на вызов без `journal` MUST NOT меняться. Непонятные записи журнала
отбрасываются и отказа не вызывают.

Все изменения контракта аддитивны: вызовы без `journal` работают как раньше, существующие ответы
без журнала не меняются, схема данных, набор статусов и допустимые переходы MUST NOT меняться.

Отказ SHALL возвращаться ошибкой инструмента с текстом `AGENT_REJECTED:<reason>`, где
`reason` из закрытого списка: `bad_request`, `not_found`, `closed`, `not_delegated`,
`not_due`, `not_in_progress`, `token_mismatch`, `bad_status`, `not_expired`.

#### Scenario: Очередь через MCP

- **WHEN** демон вызывает `agent_queue` с `today`
- **THEN** возвращаются делегированные задачи в статусе `delegated` со сроком сегодня или раньше
- **AND** задачи, зависшие в `in_progress` дольше TTL, перечислены отдельно

#### Scenario: Состояние удалённой задачи

- **WHEN** демон вызывает `agent_queue` с `task_id` удалённой задачи
- **THEN** в ответе `exists: false`

#### Scenario: Захват и завершение

- **WHEN** демон вызывает `agent_claim`, затем `agent_finish` с полученным токеном и статусом `review`
- **THEN** задача сначала `in_progress`, затем `review`
- **AND** текст добавлен в `agentNotes`

#### Scenario: Чужой токен

- **WHEN** `agent_finish` вызван с токеном, который не совпадает с токеном захвата
- **THEN** ответ — ошибка `AGENT_REJECTED:token_mismatch`
- **AND** задача не изменена

#### Scenario: Повторный захват

- **WHEN** `agent_claim` вызывается для задачи, уже взятой другим прогоном
- **THEN** ответ — ошибка `AGENT_REJECTED:not_delegated`

#### Scenario: Захват возвращает журналы прежних попыток

- **WHEN** демон вызывает `agent_claim` для задачи, у которой в `agentNotes` есть журналы с тем же сроком
- **THEN** ответ содержит `journals` рядом с `task`, не больше трёх блоков
- **AND** `task` по-прежнему состоит из `id`, `title`, `notes`, `due`

#### Scenario: Захват без журналов

- **WHEN** демон вызывает `agent_claim` для задачи без журналов
- **THEN** `journals` пустой массив

#### Scenario: Завершение с журналом

- **WHEN** демон вызывает `agent_finish` со статусом `review`, текстом и `journal`
- **THEN** в `agentNotes` журнал стоит первым блоком, за ним текст результата
- **AND** ответ содержит `journalStored: true`
- **AND** новых полей у задачи нет, `SCHEMA` равен `1`

#### Scenario: Завершение без журнала

- **WHEN** демон вызывает `agent_finish` без `journal`
- **THEN** поведение и ответ совпадают с прежними, `journalStored` в ответе нет
- **AND** контракт остальных инструментов MCP не затронут

#### Scenario: Журнал при переводе по TTL

- **WHEN** демон вызывает `agent_finish` с `by_ttl: true` и `journal` для зависшего `in_progress`
- **THEN** задача в `failed`, причина «TTL истёк»
- **AND** журнал записан в `agentNotes` под причиной, `journalStored: true`

#### Scenario: Перевод по TTL без журнала

- **WHEN** демон вызывает `agent_finish` с `by_ttl: true` без `journal`
- **THEN** поведение совпадает с прежним

### Requirement: Закрытие и перенос срока через MCP сбрасывают делегирование

Инструменты `task_done`, `task_edit` и `task_snooze` SHALL сбрасывать блок агента у задачи,
у которой он уже есть, по тем же правилам, что и клиент. Закрытие обычной задачи через
`task_done` и возврат через `undo` SHALL очищать статус агента. Закрытие повторяющейся серии
SHALL возвращать статус `delegated`, обнуляя метки захвата и завершения; `agentNotes` остаются.
Перенос срока (`task_edit` со сроком или с очисткой срока, `task_snooze`) на дату позже
сегодняшней или без срока SHALL очищать статус; перенос на сегодня или раньше MUST NOT его
менять. Для задачи без блока агента вывод и сохранённая запись MUST совпадать с прежними
байт в байт.

#### Scenario: Закрытие обычной делегированной задачи

- **WHEN** агент или пользователь вызывает `task_done` для делегированной задачи без повтора
- **THEN** задача закрыта, статус агента очищен
- **AND** `agentNotes` остались

#### Scenario: Закрытие повторяющейся делегированной задачи

- **WHEN** вызывается `task_done` для делегированной повторяющейся задачи
- **THEN** срок переносится на следующую дату серии
- **AND** статус `delegated`, метки захвата и завершения обнулены

#### Scenario: Перенос на будущую дату

- **WHEN** `task_snooze` переносит делегированную задачу на завтра
- **THEN** статус агента очищен, `agentNotes` остались

#### Scenario: Перенос на сегодня

- **WHEN** `task_snooze` переносит делегированную задачу на сегодня
- **THEN** статус агента не меняется

#### Scenario: Задача без блока агента

- **WHEN** `task_done`, `task_edit` или `task_snooze` вызваны для задачи без блока `agent`
- **THEN** вывод и сохранённая запись совпадают с теми, что были до появления делегирования

### Requirement: Контракт существующих девяти инструментов не меняется

Контракт существующих инструментов MUST остаться прежним: `tasks_list`, `task_get`, `task_add`, `task_edit`,
`task_snooze`, `task_done`, `subtask_add`, `subtask_toggle`, `task_delete`, а также `inbox_add`, `inbox_list`
и `task_comment` сохраняют имена, параметры и форму ответов. В ответы SHALL только
добавляться элементы: для не закрытых задач с блоком агента строка списка получает элемент
«агент: <статус>», а карточка задачи — строку «Статус агента: <статус>». Для задач без блока
вывод MUST NOT меняться.

#### Scenario: Контрактные тесты прежних инструментов

- **WHEN** контрактные тесты девяти инструментов прогоняются на фикстуре без поля `agent`
- **THEN** выводы совпадают с эталонными, снятыми до изменений

#### Scenario: Задача со статусом агента

- **WHEN** `tasks_list` возвращает не закрытую задачу со статусом агента
- **THEN** в её строке дополнительно указан статус агента
- **AND** остальные элементы строки прежние
