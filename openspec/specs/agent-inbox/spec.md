## Requirements
### Requirement: Входящее — запись с типом inbox

Запись SHALL иметь поле `kind` со значением `'task'` или `'inbox'`. Запись без поля `kind`
MUST считаться задачей — это обеспечивает чтение данных, созданных до появления раздела.

Входящее SHALL храниться тем же типом записи, что и задача, и ездить через тот же
`POST /api/sync`. Новых маршрутов и новой версии схемы MUST NOT появляться.

#### Scenario: Старая запись без поля kind

- **WHEN** приложение читает запись, созданную до появления «Входящих»
- **THEN** запись считается задачей и попадает в обычные разделы

#### Scenario: Входящее синхронизируется как обычная запись

- **WHEN** агент кладёт входящее, а затем открывается приложение на другом устройстве
- **THEN** входящее доезжает через обычный обмен
- **AND** `SCHEMA` остаётся равной `1`

### Requirement: У входящего нет даты и приоритета

Запись с `kind: 'inbox'` MUST NOT иметь даты: поле `due` нормализуется в `null`.
Приоритет у входящего MUST NOT считаться назначенным: поле `priority` остаётся значением
по умолчанию и не показывается в интерфейсе.

Интерфейс раздела MUST NOT давать задать входящему дату или приоритет — эти поля
появляются только при превращении в задачу.

Раздел «Входящие» SHALL быть плоским списком: без группировки по дате и без сортировки
по приоритету. Порядок — от свежего к старому по `source.at`.

#### Scenario: Агент кладёт входящее

- **WHEN** агент вызывает `inbox_add`
- **THEN** созданная запись не имеет даты
- **AND** приоритет у неё остаётся значением по умолчанию

#### Scenario: Карточка не предлагает планировать

- **WHEN** пользователь смотрит на входящее в разделе «Входящие»
- **THEN** ни дата, ни приоритет не показываются
- **AND** задать их из карточки нельзя

#### Scenario: Входящее не появляется среди задач

- **WHEN** во «Входящих» лежит неразобранная запись
- **THEN** она не появляется ни в одном разделе задач, включая «Все задачи»

### Requirement: Активная запись без даты — входящее

Активная запись с пустым `due` MUST иметь `kind: 'inbox'`. Правило SHALL действовать
на любом пути создания и изменения записи — из интерфейса, из быстрого ввода, из MCP —
и MUST выполняться нормализацией, а не отдельными проверками в местах вызова.

Задача, у которой сняли дату, SHALL возвращаться во «Входящие» на разбор.

Выполненные записи MUST NOT попадать под это правило: завершённая запись без даты
остаётся в «Выполнено» и не становится входящим.

Раздела «Без даты» MUST NOT существовать: `VIEWS.someday` убирается, группа «Без даты»
исчезает из раздела «Все задачи».

#### Scenario: Задача создана без даты

- **WHEN** пользователь создаёт задачу, не указав день
- **THEN** запись получает `kind: 'inbox'`
- **AND** появляется во «Входящих»

#### Scenario: С задачи сняли дату

- **WHEN** у задачи с датой дату убрали
- **THEN** запись возвращается во «Входящие»

#### Scenario: Старые записи без даты не теряются

- **WHEN** приложение читает данные, созданные до этой работы, где есть активные задачи
  без даты
- **THEN** они становятся входящими и видны во «Входящих»
- **AND** ни одна из них не пропадает из интерфейса

#### Scenario: Выполненное без даты остаётся выполненным

- **WHEN** в данных есть завершённая задача без даты
- **THEN** она остаётся в разделе «Выполнено»
- **AND** во «Входящих» не появляется

### Requirement: Входящее помнит свой источник

Входящее SHALL хранить поле `source` вида `{ kind, url, title, ref, at }`, где `kind` —
один из `gmail`, `telegram`, `web`, `calendar`, `agent`, `manual`.

Интерфейс SHALL давать переход к источнику по `source.url` — к письму в Gmail, сообщению
в телеграме, странице в вебе.

#### Scenario: Переход к источнику

- **WHEN** пользователь нажимает переход к источнику на карточке входящего
- **THEN** открывается адрес из `source.url`

#### Scenario: Источник переживает превращение в задачу

- **WHEN** входящее превращается в задачу
- **THEN** поля `source` и `agentNotes` сохраняются
- **AND** у задачи остаётся память о том, откуда она взялась

### Requirement: Заметки агента отделены от заметок человека

Запись SHALL иметь поле `agentNotes` — ленту вида `[{ at, text }]`, куда пишет агент.

Агент MUST NOT править поле `notes`, которое пишет человек. Текст пользователя
остаётся неприкосновенным.

#### Scenario: Агент дописывает контекст

- **WHEN** агент вызывает `task_comment` для существующей задачи
- **THEN** запись появляется в `agentNotes`
- **AND** поле `notes` не изменяется

#### Scenario: Обе ленты видны в карточке

- **WHEN** у входящего есть и заметка агента, и заметка человека
- **THEN** интерфейс показывает их раздельно, различимо по происхождению

### Requirement: Повторное добавление обновляет, а не плодит

`inbox_add` SHALL дедуплицировать по `source.ref`. Если входящее с таким `ref` уже
существует, инструмент MUST обновить его, а не создать вторую запись.

Для писем `ref` — `Message-ID`, для телеграма — `chat_id:message_id`.

#### Scenario: Повторный разбор той же почты

- **WHEN** агент второй раз разбирает ту же папку и снова вызывает `inbox_add` с тем же `ref`
- **THEN** существующее входящее обновляется
- **AND** второй записи не появляется

#### Scenario: Входящее без ref

- **WHEN** агент кладёт входящее без `source.ref`
- **THEN** запись создаётся как новая, дедупликация не применяется

### Requirement: Разбор входящего оставляет решение за человеком

Входящее MUST NOT превращаться в задачу автоматически. Превращение SHALL происходить
только действием человека — при планировании или через карточку раздела.

Превращение SHALL менять `kind` на `'task'` и сохранять `source` и `agentNotes`.
«Отбросить» SHALL выполнять обычное удаление с надгробием и возможностью отменить через тост.

#### Scenario: Превращение через карточку раздела

- **WHEN** пользователь выбирает «В задачу» на карточке входящего
- **THEN** `kind` становится `'task'`
- **AND** открывается редактор задачи с полями даты и приоритета

#### Scenario: Отброшенное можно вернуть

- **WHEN** пользователь выбирает «Отбросить»
- **THEN** запись удаляется с надгробием
- **AND** тост позволяет отменить удаление

#### Scenario: Ничего не превращается само

- **WHEN** входящее пролежало неразобранным сколько угодно долго
- **THEN** оно остаётся входящим и не появляется среди задач

### Requirement: Разбор входящих — часть планирования

Moments SHALL вести по одной очереди, в начале которой идут неразобранные входящие,
а затем задачи в существующем порядке (просроченные, затем на сегодня). Задач без даты
в очереди MUST NOT быть — таких записей не существует.

Карточка входящего SHALL задавать те же вопросы, что и карточка задачи — «когда делать»
и «какой приоритет», — и дополнительно показывать источник и ленту `agentNotes`.
Отдельного набора ответов для входящих MUST NOT быть.

Ответ на вопрос «когда» SHALL превращать входящее в задачу: `kind` меняется на `'task'`
тем же действием, которое проставляет дату.

Пропуск карточки MUST оставлять запись входящей — она вернётся в очередь при следующем
проходе.

#### Scenario: Входящие идут первыми

- **WHEN** пользователь открывает Moments и во «Входящих» что-то лежит
- **THEN** сначала показываются входящие
- **AND** затем задачи в обычном порядке

#### Scenario: Планирование превращает входящее в задачу

- **WHEN** пользователь выбирает дату на карточке входящего в Moments
- **THEN** `kind` становится `'task'`
- **AND** дата и приоритет сохраняются у получившейся задачи

#### Scenario: Пропущенное остаётся входящим

- **WHEN** пользователь пропускает карточку входящего
- **THEN** запись остаётся входящей
- **AND** попадает в очередь следующего прохода

#### Scenario: Проход с пустыми входящими

- **WHEN** во «Входящих» пусто
- **THEN** очередь состоит только из задач и выглядит как раньше
